小团队 AI 产品落地的技术选型与架构瘦身
FDE 必修课里，小团队做 AI 产品落地，第一道难关不是模型能力，而是技术选型。大厂可以堆资源、堆团队、堆自研，小团队必须反过来：用最小成本验证最大价值。技术选型的核心原则只有四个：场景优先、可替换、最小闭环、成本可控。不要因为某个模型热门就选它，也不要因为某个框架先进就上它。小团队的目标是尽快让真实用户用起来，而不是搭建一套看起来完整的 AI 平台。

架构上，AI 产品通常包含交互层、编排层、模型层、数据层、工具层和治理层。但小团队不能一开始就做六层微服务。更合理的路径是：先单体，后拆分；先 API，后自训；先 RAG，后微调；先工作流，后 Agent。交互层可以是一个简单的前端或聊天入口；编排层先把提示组织、检索、工具调用串起来；模型层优先使用成熟闭源 API，同时保留开源模型备选；数据层先做最小知识库和权限过滤；工具层只连接真正必要的业务系统；治理层先覆盖日志、审计和基础安全。架构瘦身不是偷懒，而是把资源集中在验证业务价值上。

模型选型要避免“唯最强论”。小团队应建立模型路由思维：简单分类、抽取、改写走小模型或缓存；复杂推理、多轮规划走强模型；敏感数据走私有化或本地模型；高并发场景走批处理或异步队列。模型不是越贵越好，而是要在质量、延迟、成本之间找到业务可接受的平衡点。更重要的是可替换性：提示模板、模型接口、评测标准要尽量解耦，避免被单一供应商锁死。

数据与上下文工程是小团队最容易忽视、也最容易拉开差距的环节。AI 产品效果往往不取决于模型本身，而取决于喂给模型的上下文。知识库要清洗、切分、嵌入、更新和权限隔离；业务数据要实时同步、脱敏和版本化；多轮对话要状态管理和摘要压缩。检索质量、重排策略、引用溯源和拒答机制，直接决定用户是否信任产品。小团队不必一开始追求大而全的数据平台，但必须保证关键数据准确、可更新、可追溯。

工具集成要少而精。每接入一个工具，就多一份权限、失败处理、审计和运维成本。优先接入高频、高价值、接口稳定的系统，并定义清晰的输入输出、权限边界、超时重试和幂等策略。危险操作必须二次确认，敏感动作必须留痕。小团队没有专门的安全团队，更要把最小权限、沙箱隔离、密钥管理和操作审计做成默认习惯。

最后是人机协同与交付节奏。小团队 AI 产品不应追求全自动，而应追求可解释、可控制、可恢复的自动闭环。人负责目标、价值判断、风险接受和最终验收；AI 负责信息整理、方案生成、重复执行和初步验证。技术上先跑通一周原型，再用两周小范围试点，最后用一个月打磨生产版本。每一次迭代都围绕真实反馈，而不是围绕技术炫技。小团队的优势是快，但快必须建立在架构瘦身、边界清晰和可替换的基础上。谁能用最小系统跑通真实场景，谁就能在 AI 产品落地中活下来。
